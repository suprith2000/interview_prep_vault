### How Elasticsearch Writes Data

Elasticsearch uses a distributed, near real-time architecture to write and index data. When a write request is made, the process involves a sequence of steps to ensure data consistency, fault tolerance, and quick availability for search. The writing process involves indexing, creating/updating documents, distributing data across nodes and shards, and managing data replication. Here’s a breakdown of how Elasticsearch writes data:

---

### 1. **Document Structure and Indexing**

In Elasticsearch, data is stored as **JSON documents**. When writing data, each document is indexed into a specific **index**. An index is a logical namespace that contains similar documents, and it’s physically divided into **shards** for horizontal scalability.

- **Index**: The main logical container that stores data (analogous to a database).
- **Document**: The individual data unit (a row or record).
- **Field**: Each key-value pair within a document (a column).

### 2. **Sharding: Data Distribution**

When a document is indexed, it is assigned to a specific **shard** within an index. Elasticsearch uses **sharding** to distribute the data across multiple nodes for horizontal scalability. Each shard is essentially a separate Lucene index.

- **Primary Shard**: The original shard where data is written.
- **Replica Shard**: A copy of the primary shard used for fault tolerance and load balancing. Writes to the primary shard are propagated to its replica shards.

---

### 3. **Write Operation Types**

Elasticsearch supports several types of write operations:

- **Indexing (Create/Update)**: Adding or updating documents in an index.
- **Bulk Writes**: Writing multiple documents in a single request for efficiency.
- **Deletes**: Removing a document from an index.

---

### 4. **Writing Data: Steps of the Write Process**

When you send a write request to Elasticsearch, the process involves several key steps:

#### 4.1. **Routing**

When a document is written, Elasticsearch determines the specific **shard** where the document will be stored using a **routing algorithm**. The default routing is based on the document's **_id** field, but custom routing can also be specified.

- **Routing formula**: `(hash(_routing) % number_of_primary_shards)`

This ensures that each document is deterministically assigned to a specific shard based on its ID or a custom routing field.

#### 4.2. **Coordinating Node**

The node that receives the write request acts as the **coordinating node**. This node’s responsibility is to:

- Route the document to the appropriate **primary shard** (using the routing algorithm).
- Manage the write request by interacting with other nodes in the cluster.

#### 4.3. **Primary Shard Write**

The document is sent to the **primary shard** where it will be indexed. The primary shard does the following:

- **Check for Document Existence**: If the document already exists (identified by its **_id**), the existing document will be updated; otherwise, a new document will be created.
- **Versioning**: Elasticsearch uses a versioning system to ensure consistency. Each document has a version number that is incremented with each update. This helps with handling conflicts in distributed systems.
- **Document Indexing**: The document is tokenized and added to the **inverted index**. The inverted index allows for efficient search queries later.

#### 4.4. **Replica Shard Write**

Once the document is successfully written to the **primary shard**, it is then asynchronously replicated to all of the associated **replica shards**. This provides redundancy and fault tolerance.

- **Replication**: Elasticsearch ensures that every primary shard has at least one or more replica shards (if configured). These replicas are exact copies of the primary shard.
- **Consistency**: Elasticsearch uses a quorum-based replication mechanism to ensure consistency across primary and replica shards.

#### 4.5. **Acknowledgment**

After the document is written to the primary shard and replicated to the replica shards, the **coordinating node** receives an acknowledgment of success. The acknowledgment is then sent back to the client to indicate that the write operation has completed successfully.

**Note**: By default, Elasticsearch waits for acknowledgment from the primary shard but does not wait for acknowledgment from the replica shards. This behavior can be configured with the **replication factor** and the **write consistency** settings.

---

### 5. **Near Real-Time Indexing**

Elasticsearch is a near real-time search engine, meaning that the data you write to it becomes available for search shortly after the write operation. This is because Elasticsearch uses a **refresh interval** to control when newly indexed data is made searchable.

- **Refresh Interval**: The default refresh interval is 1 second. When a document is written, it is first stored in an **in-memory buffer** and an **inverted index** is created. After each refresh, Elasticsearch writes the data from the in-memory buffer to a new **Lucene segment** on disk.
- **Segments**: These are immutable chunks of data that hold indexed documents. Segments are periodically merged into larger segments to optimize search performance and minimize disk I/O.

---

### 6. **Bulk Writes for Efficiency**

Elasticsearch supports **bulk indexing**, which allows multiple documents to be written in a single request. Bulk indexing is more efficient than sending individual write requests because it reduces overhead and optimizes network communication.

- **Bulk API**: Elasticsearch provides a bulk API that allows you to perform multiple create, update, and delete operations in a single API call. This reduces the number of requests between the client and the Elasticsearch cluster.

---

### 7. **Document Updates**

When updating a document, Elasticsearch does not overwrite the original document directly. Instead, it performs a process called **reindexing**.

- **Reindexing Process**:
    - A new version of the document is created with the updated fields.
    - The new document is indexed as a new document in a new segment.
    - The old version of the document is marked as deleted and will be removed during the next **segment merge**.

This approach ensures that documents are never modified in place, maintaining the immutability of segments. Over time, deleted documents are cleaned up as part of the segment merging process.

---

### 8. **Deletes in Elasticsearch**

Deleting a document in Elasticsearch does not immediately remove it from disk. Instead, the document is marked as deleted in the current segment, and it will continue to exist until a **segment merge** occurs.

- **Soft Deletes**: Elasticsearch uses a "soft delete" mechanism, meaning that documents are flagged for deletion but are not removed immediately. This allows for faster delete operations and also facilitates features like **document versioning** and **index rollback**.
- **Merge Process**: During periodic segment merges, documents marked for deletion are purged from the index.

---

### 9. **Write Conflicts and Version Control**

Elasticsearch uses a **versioning system** to handle concurrent write operations. Every document has a version number, which is incremented every time the document is updated. This ensures **optimistic concurrency control**, which prevents overwriting data during conflicting write operations.

- **Version Conflict**: If two clients attempt to update the same document concurrently, Elasticsearch detects the version conflict and can either reject the operation or resolve it based on the configuration.
- **Optimistic Locking**: Elasticsearch supports optimistic locking, where the client specifies the expected version of the document. If the document version in Elasticsearch does not match the expected version, the write is rejected.

---

### 10. **Durability and Write-Ahead Log (Translog)**

Elasticsearch ensures durability (data is not lost even in case of a crash) using a **translog** (transaction log) mechanism.

- **Translog**: Before a write operation is acknowledged as successful, Elasticsearch writes the document to a **translog** on disk. This ensures that even if the node crashes before the data is committed to a segment, it can be recovered from the translog.
- **Commit Process**: After each successful write, Elasticsearch periodically commits the translog data to disk and clears it. This process is called a **flush**.

---

### Summary: How Elasticsearch Writes Data

- **Coordinating Node**: Receives the write request and routes the document to the appropriate primary shard based on routing.
- **Primary Shard**: Receives the document, indexes it, and stores it in an in-memory buffer and translog.
- **Replica Shards**: Asynchronously receive the document and index it to ensure fault tolerance.
- **Acknowledgment**: Once the primary shard has successfully written the document, the acknowledgment is sent to the client.
- **Segments and Refresh**: Documents are written to disk in segments, and they become searchable after the refresh interval.
- **Bulk Writes**: Elasticsearch supports bulk operations for efficiency, reducing the overhead of individual write requests.
- **Versioning**: Elasticsearch uses a version control system to handle concurrent writes and prevent conflicts.

This approach ensures that Elasticsearch can handle large-scale data ingestion while maintaining consistency, high availability, and fast query performance.
