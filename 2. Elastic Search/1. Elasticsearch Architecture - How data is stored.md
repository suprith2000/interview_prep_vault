
In Elasticsearch, data is stored in a **distributed, document-based architecture**, optimized for full-text search and real-time data retrieval. Here’s how data is structured and stored:

### 1. **Cluster**

- **Cluster**: A cluster is a collection of one or more nodes that together hold the entire dataset and provide distributed indexing and search capabilities. Each cluster has a unique name to distinguish it from others.
- **Node**: A node is a single server that is part of a cluster and stores data. Nodes can be of different types (master, data, or client nodes).

### 2. **Index**

- An **index** is similar to a database in relational databases. It is a logical namespace where Elasticsearch stores related documents. You can have multiple indices for different types of data, and each index has a unique name.

### 3. **Document**

- A **document** is the basic unit of information stored in Elasticsearch. It is represented in JSON format and contains fields like a record in a relational database.
- Each document is stored in an **index** and identified by a unique **ID**.
- Documents are schema-less, meaning you don't have to define a schema beforehand, but they can have mappings that define the structure of the fields.

### 4. **Shards and Replicas**

- **Shards**: Elasticsearch breaks an index into smaller parts called **shards** to distribute data across multiple nodes. This allows for parallel processing and horizontal scaling. Each shard is a fully functional and independent index that can be hosted on any node.
    - **Primary Shards**: These store the original data of an index.
    - **Replica Shards**: These are copies of primary shards that provide high availability and fault tolerance.
- The number of primary and replica shards is defined when an index is created.

### 5. **Segments**

- Inside each shard, Elasticsearch stores data in **segments**. A segment is an immutable, small part of the inverted index, which holds data on how terms map to documents.
- As new documents are added, Elasticsearch writes them to a new segment. Over time, segments are merged to optimize performance and minimize storage overhead.

### 6. **Inverted Index**

- The **inverted index** is the core structure behind Elasticsearch’s search capabilities. Instead of storing documents as rows (like in traditional databases), Elasticsearch stores the mapping of **terms** (keywords) to the **document IDs** that contain them.
- For example, if a document contains the word “cat,” the inverted index maps “cat” to the document ID where it appears. This allows Elasticsearch to quickly retrieve all documents that match a search query.

### 7. **Mappings**

- **Mappings** define the structure and data types of the fields within documents, like specifying which fields are text, numbers, dates, etc.
- Mappings also define how the data will be indexed, such as whether fields should be searchable, analyzed, or tokenized.

### 8. **Lucene Storage**

- Elasticsearch uses **Apache Lucene** under the hood for data storage and retrieval. Lucene handles the actual low-level indexing and searching, while Elasticsearch provides a distributed and high-level interface for interacting with the data.

### 9. **Storage Types**

- Elasticsearch stores data either in **disk-based storage** or **in-memory structures** depending on configurations and use cases. By default, it stores data on disk to allow persistence and durability.

### Example Workflow:

1. **Indexing a document**: When you add a document, Elasticsearch stores it in a primary shard and replicates it to the replica shards. The document is indexed, meaning an entry is added to the inverted index for fast retrieval.
2. **Searching a document**: When a search query is executed, Elasticsearch queries all the shards that hold the index and merges the results to return the most relevant documents.

This distributed approach ensures that Elasticsearch can scale easily, handle large volumes of data, and deliver fast search results.
